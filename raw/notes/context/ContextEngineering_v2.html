01 · 무엇이 다른가
같은 일도 책상 위가 다르면 결과가 달라진다
AI의 지식은 이미 충분하다. 성능을 가르는 것은 작업 기억, 즉 지금 이 일을 위해 책상 위에 올라와 있는 정보다.

"이거 좀 해봐." 프롬프트 엔지니어링

01 · 무엇이 다른가
컨텍스트 엔지니어링이란
프롬프트 엔지니어링의 다음 단계로, 프롬프트 외의 정보까지 포함해 추론 과정에서 최적의 정보를 선별하고 유지하는 전략 Anthropic, Effective context engineering for AI agents 설명 요약

질문무엇을 어떻게 말할까지금 무엇을 보여 주고 무엇을 치울까

둘의 관계 한 줄 — 컨텍스트 엔지니어링은 프롬프트 엔지니어링의 범위를 지시문 밖으로 넓힌 것이다. 지시문은 컨텍스트의 일부로 남는다.

왜 이제 필요한가

에이전트는 정보를 계속 만들어낸다. 검색 결과, 도구 실행 결과, 다른 에이전트의 결과가 모두 컨텍스트 후보다. 전부 유지할 수도 없고, 오래됐다는 이유만으로 버릴 수도 없다.

그래서 선별과 관리가 기술이 된다

어떤 정보는 그대로 유지하고, 긴 기록은 압축하고, 반복되는 부분은 재사용하고, 필요할 때 다시 찾는다. 이 흐름을 설계하는 일이 작업의 핵심이다.

02 · 왜 중요한가
문제 1 · 작업 기억에는 한계가 있다
컨텍스트 윈도우는 AI의 작업 책상이다. 이 책상은 3년 사이 250배 커졌다. 그런데도 같은 말을 반복하게 된다.

넓어졌다고 편해지지 않는다

사람도 넓은 책상만으로는 일하지 못한다. 지금 필요한 것이 책상 위에 올라와 있어야 쓸 수 있다. LLM도 마찬가지다.

길게 넣으면 가운데가 빠진다

긴 입력을 한 번에 넣으면 처음과 끝은 잘 쓰이고 가운데는 놓친다. 스탠퍼드 연구에서는 관련 정보를 가운데 두었을 때 GPT-3.5-Turbo의 정확도가 문서 없이 물었을 때(56.1%)보다 낮아졌다.

자동 요약이 시작되는 지점에서 원본이 사라지고 성능이 떨어지기 시작한다. 그래서 오래 쌓은 컨텍스트보다 새로 시작한 컨텍스트가 낫다.
Liu et al. — Lost in the Middle, TACL 2023 · Chroma — Context Rot (2025.07)
02 · 왜 중요한가
문제 2 · 컨텍스트는 다섯 가지 방식으로 망가진다
창이 100만 토큰까지 열렸지만 많이 넣는다고 잘 되지는 않는다. 에이전트는 검색, 도구 호출, 긴 히스토리가 동시에 쌓여서 아래 실패가 겹치기 쉽다.
01
맥락 부패
context rot
입력이 길어질수록 성능이 고르게 떨어진다.
근거 Chroma가 18개 모델을 비교했다. 단어를 그대로 복사하는 단순한 과제에서도 입력이 길수록 정확도가 떨어졌다.
02
맥락 중독
poisoning
한 번 틀린 정보가 컨텍스트에 굳어져 계속 참조된다.
근거 Gemini 2.5 리포트에서 포켓몬 에이전트가 게임 상태를 잘못 기억한 뒤, 달성 불가능한 목표에 집착하며 같은 행동을 반복했다.
03
맥락 방해
distraction
컨텍스트에 끌려 학습으로 얻은 판단력을 쓰지 못하고 과거 행동을 반복한다.
근거 Gemini 2.5는 10만 토큰을 넘기면 새 계획 대신 과거 행동을 따라 했다. Databricks는 32k 부근에서 정확도 하락을 보고했다.
04
맥락 혼란
confusion
관련 없는 정보가 답에 끼어든다. 대표 사례는 도구가 많을수록 나빠지는 경우다.
근거 Berkeley BFCL에서 모든 모델이 도구 2개 이상이면 성능이 떨어졌다. 도구 46개를 주면 실패하고 19개면 성공한 사례가 있다.
05
맥락 충돌
clash
관련 없는 정도가 아니라 서로 모순되는 정보가 함께 있다. 앞선 턴에서 모델이 내놓은 오답이 남아 있어, 나중에 정보를 모두 줘도 나쁜 답을 낸다.
근거 Microsoft · Salesforce 실험에서 정보를 여러 턴에 나눠 주자 평균 39% 하락했다. o3은 98.1에서 64.1로 떨어졌다.
dbreunig — How Long Contexts Fail (2025.06) · Chroma — Context Rot (2025.07) · Databricks · Berkeley BFCL
02 · 왜 중요한가
비용 · 돈이 새는 곳은 타이핑한 프롬프트가 아니다
토큰은 비용이지 성과가 아니다. 에이전트에서는 눈에 보이지 않는 곳에서 토큰이 쓰인다.

1 · 출력

코드 한 줄을 찾는 데 5분짜리 설명이 돌아오면 토큰이 들고 읽는 시간도 든다. 그 답은 다음 턴에 컨텍스트로 되돌아온다. 돈과 시간을 두 번 쓴다.

2 · 입력

매뉴얼, 대화 기록, 통파일을 통째로 넣으면 필요한 부분만 찾아 쓸 때보다 비용이 최대 82배 들었다는 사례가 있다 (외부 발표 인용 · 워크로드와 요금 조건에 따라 다름).

3 · 보이지 않는 비용

컨텍스트가 지저분해져 세션이 일찍 끝나면 새 대화에서 처음부터 다시 설명해야 한다. 결제 내역에는 나오지 않는 시간 손실이다.

프롬프트만 줄여서는 한계가 있다

사용자 입력은 한 줄이어도 모델이 실제로 처리하는 것은 User Prompt + Rules + History + Code + RAG + Tools + Agent Results다.

요금에도 이미 드러난다

많은 서비스가 긴 입력에 할증을 붙이고, 반복되는 앞부분(prefix)은 캐시 단가를 낮게 받는다 (모델별 상이, 공식 가격표 확인). 처리할 수 있는 범위와 작업에 맞는 크기는 다르다.

03 · 컨텍스트를 다스리는 법
덜어내기 · Context Pruning
에이전트가 오래 일하면 검색 결과, 도구 출력, 대화 기록이 계속 쌓인다. 이 중 지금 가치가 사라진 것을 걷어낸다.

걷어낼 것

  • 이미 해결된 작업의 상세 로그
  • 현재 판단과 관계없는 검색 결과
  • 몇 단계 뒤부터 의미를 잃은 내용
  • 도구가 돌려준 수백 줄 중 판단에 필요한 몇 줄을 뺀 나머지

일괄 압축이 아니다

전체를 한꺼번에 줄이는 것이 아니라, 작업이 진행되면서 가치가 낮아진 정보만 정리한다.

다음 슬라이드의 압축은 아직 필요한 정보를 줄이는 작업이고, 덜어내기는 쓸모가 없어진 정보를 빼는 작업이다.

이렇게 하면 문제가 생긴다

원인을 추적하는 데 필요한 로그나 예외 처리 분기까지 지워 버리는 경우다. 무엇을 지울지는 그때그때 정하지 말고 기준을 미리 적어 둔다.

기준은 문장으로 적을 수 있어야 한다

최근 N턴 · 현재 목표와 무관한 파일 · 해결 완료된 이슈 — 이렇게 적을 수 있어야 자동화할 수 있다.

빈 책상 늘리기 · 서브에이전트
서브에이전트(분신)는 빈 새 책상에서 시작한다. 메인의 서류를 한 장도 가져가지 못한다. 이것이 장점이면서 제약이다.

이렇게 쓴다

  • 완전히 독립적인 일에만 쓴다. 자료 조사, 예제 수집, 후보 비교가 해당한다
  • 지시는 평소보다 길게 쓴다. 무엇을, 왜, 어디까지인지 적고 대화를 못 봤다고 가정한다
  • 보고는 "다 했습니다"로 끝내지 않는다. 무엇을 발견했고 어떻게 고쳤고 왜 그렇게 판단했는지 받는다
  • 물리적 분리가 필요하면 worktree로 폴더를 복사해 병렬로 돌린다

최악의 패턴

CEO, 디자이너, 테스터처럼 역할별 조직도를 세우는 것이다.

테스터는 메인의 맥락이 필요한데 서브에이전트의 책상에는 그게 없다. 그래서 엉뚱한 곳을 치우게 된다.

판단 기준은 하나다. 메인 책상의 정보 없이도 일이 끝나는가.

메인이 깨끗해진다

탐색과 비교 같은 잡일이 메인 책상에서 사라진다.

세션이 오래 간다

30분 만에 끝나던 대화가 2시간 유지되었다는 사례가 있다 (외부 발표 인용). 자동 압축이 시작되는 시점도 늦춰진다.

검토는 두 단계로

서브에이전트가 지시대로 했는지, 결과의 품질이 충분한지를 따로 확인한다.

서브에이전트는 인력을 늘리는 일이 아니라 깨끗한 책상을 늘리는 일이다.
03 · 컨텍스트를 다스리는 법
구조화하기 · 책상을 쪼개고 필요할 때 펼치게 한다
100줄짜리 매뉴얼을 통째로 올리면 제대로 읽히지 않는다. 목차만 보고 필요한 챕터만 펼치게 하면 자원이 40~60% 줄었다는 사례가 있다 (외부 발표 인용).

1 · 파일당 50줄 안팎으로 쪼갠다

  • 목차는 맨 위에 두고, 본문은 호출될 때만 읽히게 한다
  • 전체 규칙과 프로젝트 규칙의 2층으로 나누고 더 좁은 쪽을 우선한다
  • 맨 위에 절대 규칙 섹션을 하나 둔다
  • 같은 실수가 두 번 나오면 AI에게 매뉴얼을 고치게 한다

2 · 훅으로 강제로 펼친다

규칙을 적어 놓아도 읽지 않으면 소용이 없다. 읽도록 강제한다.

훅동작
앞 훅지시 직전에 관련 매뉴얼을 끼워 넣는다
뒤 훅작업이 끝난 뒤 오류와 보안 누락이 없는지 되묻는다

발동 조건은 키워드 · 의도 · 위치 · 파일 내용 네 가지로 판단한다.

3 · 기억을 파일로 남긴다

착수 전에 계획서, 맥락 노트, 할 일 세 가지를 파일로 남긴다. 승인 시점에 멈추고 문서 저장 → 새 대화 → 읽고 이어하기 순서로 진행한다. 한 번에 다 시키지 말고 한두 개씩 확인한다.

4 · 자주 비운다

  • 자동 요약을 기다리지 말고 일이 끝나면 바로 비운다
  • 노트에는 관련 있는 것만 남긴다
  • 도구를 한꺼번에 설치하지 않는다. 안 쓰는 도구 설명서가 매번 올라온다
개인 규칙 파일은 매 세션마다 읽힌다. 여기서 줄인 토큰은 세션마다 누적된다.

1 · 컨텍스트 사용량을 확인한다

지금 이 대화에서 컨텍스트가 몇 %나 찼는지 본다. 50%를 넘으면 정리하고 새 대화로 넘어간다. 턴마다 전체 기록이 다시 입력되므로 긴 대화일수록 토큰이 빠르게 쌓인다.

설정: 컨텍스트 사용량 표시를 하단에 항상 켜 둔다

2 · 작업을 더 작게 쪼갠다

한 번에 하나만 시킨다. 1 PR에 1 작업이 기준이다. 작업이 커질수록 컨텍스트가 일찍 차고 결과물도 읽기 어려워진다.

목표: 세션이 2시간 유지되게 만들기

3 · 과한 규칙 파일을 쪼갠다

CLAUDE.md가 200줄이면 제대로 읽히지 않는다. 50줄과 목차로 나누고 필요한 챕터만 펼치게 한다.

목표: 규칙 파일 하나를 50줄 이내로

4 · 끝난 작업은 컨텍스트에 남기지 않는다

끝난 일의 로그, 이미 고친 버그, 지난 검색 결과는 다음 질문에 쓰이지 않는다. 결정과 그 이유만 파일에 남기고 나머지는 비운다.

목표: 일이 끝나면 바로 비우기

정리 · 원칙 세 가지
01

신선하게

쌓아 둔 것보다 지금 필요한 것을 쓴다. 자동 요약을 기다리지 말고 끝나면 비운다. 같은 리액트 질문의 응답이 1,214토큰과 294토큰으로 갈린 것도 무엇을 넣고 뺐느냐의 차이였다 (외부 발표 인용).

02

압축되게

원문을 다 남기는 것이 목적이 아니다. 판단의 근거를 남긴다. 무엇을 시도했고, 무엇이 실패했고, 왜 그렇게 정했는지만 있으면 다음 판단이 이어진다.

03

관련 있게

지금 하는 일과 무관한 것은 책상 밖에 둔다. 도구를 많이 연결하고 로그를 다 남기는 것은 오히려 방해가 된다. 창의 크기보다 필요한 것을 어디에 두느냐가 중요하다.

이렇게 하지 않는다
100만 토큰을 다 채운다

창이 커졌다고 여유가 생기는 것은 아니다. 관련 없는 정보가 자리를 차지하고, 앞선 오답이 최종 답을 흔든다.

이렇게 한다
지금 필요한 것만 둔다

덜어내고, 압축하고, 필요할 때 찾아오게 하고, 독립된 일은 다른 책상에서 처리한다.

한 줄 요약
AI의 지식은 충분하다.
성능은 책상 위에 무엇을 올려두느냐에 달려 있다.

프롬프트는 지시문을 정한다

무엇을 말할지 결정한다. 한 줄이지만 결과에 영향을 준다.

컨텍스트는 작업 환경을 정한다

무엇을 보여 주고 무엇을 치울지 결정한다. 작업 전체에 걸친다.

둘은 이어진다
